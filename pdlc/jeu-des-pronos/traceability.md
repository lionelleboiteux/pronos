## 3. API contract — both sides

Tooling is exactly what `02-architecture.v1.md` §5 names: **Prism** for the
consumer side, **Schemathesis** for the provider side, both generated from
`contracts/openapi.yaml` at run time.

| Operation | Method + path | Consumer test (Prism) | Provider test (Schemathesis) |
|---|---|---|---|
| `listLeagues` | `GET /v1/leagues` | `CONTRACT-CONSUMER-listLeagues` | `CONTRACT-PROVIDER-listLeagues` |
| `getCurrentGameweek` | `GET /v1/leagues/{leagueId}/current` | `CONTRACT-CONSUMER-getCurrentGameweek` | `CONTRACT-PROVIDER-getCurrentGameweek` |
| `submitPrediction` | `POST /v1/predictions` | `CONTRACT-CONSUMER-submitPrediction` (+ the 409 `MATCH_LOCKED` branch) | `CONTRACT-PROVIDER-submitPrediction` |
| `getGameweekStandings` | `GET /v1/leagues/{leagueId}/gameweeks/{gameweekId}/standings` | `CONTRACT-CONSUMER-getGameweekStandings` | `CONTRACT-PROVIDER-getGameweekStandings` |
| `getOverallStandings` | `GET /v1/leagues/{leagueId}/seasons/{seasonId}/standings/overall` | `CONTRACT-CONSUMER-getOverallStandings` | `CONTRACT-PROVIDER-getOverallStandings` |
| `listDuplicateFlags` | `GET /v1/admin/duplicate-flags` | `CONTRACT-CONSUMER-listDuplicateFlags` (+ the 401 `UNAUTHORIZED` branch) | `CONTRACT-PROVIDER-listDuplicateFlags` |
| `updateDuplicateFlagStatus` | `PATCH /v1/admin/duplicate-flags/{flagId}` | `CONTRACT-CONSUMER-updateDuplicateFlagStatus` | `CONTRACT-PROVIDER-updateDuplicateFlagStatus` |
| `overrideGameweek` | `POST /v1/admin/gameweeks/{gameweekId}/override` | `CONTRACT-CONSUMER-overrideGameweek` | `CONTRACT-PROVIDER-overrideGameweek` |

`CONTRACT-COVERAGE: every operation declared in openapi.yaml has a consumer
test in this file` is a guard test that fails if an operation is ever added to
the contract without a consumer test. **It is the one test in the suite that
passes at red**, because it reads only the already-delivered contract artifact.

Datastore contract (`contracts/db-schema.sql`): consumer side is not a process
boundary (same trust boundary — §5), so there is no consumer test. The provider
side is `tests/db/schema.test.ts`, which applies the **production migrations**
(`db/migrations/*.sql`) to a real Postgres 16 — §5's "migration tests at red".

## 4. Telemetry events

All 8 events from `state.json` `success.required_events`. Shape and both
emission directions are covered, because an event that only fires on success
cannot produce a completion rate — the denominator would be missing.

| Event | Shape test | Storage test | Positive emission | Negative emission |
|---|---|---|---|---|
| `match_locked` | `TELEMETRY-match_locked: builds a telemetry_events row…` | `TELEMETRY-match_locked: the telemetry_events store accepts this required event type` | `TELEMETRY-match_locked: the tick emits match_locked for a match whose kickoff has just passed` | `TELEMETRY-match_locked (negative): a match already reported as locked is not re-emitted on a later tick, so lock counts cannot inflate` |
| `prediction_submitted` | `TELEMETRY-prediction_submitted: builds a telemetry_events row…` | same pattern | `TELEMETRY-prediction_submitted: an accepted submission emits exactly one prediction_submitted event` | `TELEMETRY-prediction_submitted (negative): a submission rejected as late emits no prediction_submitted event` |
| `prediction_rejected_late` | `TELEMETRY-prediction_rejected_late: builds a telemetry_events row…` | same pattern | `TELEMETRY-prediction_rejected_late: a 409 MATCH_LOCKED rejection emits exactly one prediction_rejected_late event` | `TELEMETRY-prediction_rejected_late (negative): an accepted submission emits no prediction_rejected_late event` |
| `gameweek_opened` | `TELEMETRY-gameweek_opened: builds a telemetry_events row…` | same pattern | `TELEMETRY-gameweek_opened: the next gameweek becoming open emits exactly one gameweek_opened event` | `TELEMETRY-gameweek_opened (negative): closing the season's last gameweek emits no gameweek_opened event, since nothing opened` |
| `gameweek_closed` | `TELEMETRY-gameweek_closed: builds a telemetry_events row…` | same pattern | `TELEMETRY-gameweek_closed: closing a gameweek emits exactly one gameweek_closed event` | `TELEMETRY-gameweek_closed (negative): a tick before the last kickoff emits no gameweek_closed event` |
| `scoring_run_completed` | `TELEMETRY-scoring_run_completed: builds a telemetry_events row…` | same pattern | `TELEMETRY-scoring_run_completed: a completed scoring run emits one event carrying players_scored_count` | `TELEMETRY-scoring_run_completed (negative): a run skipped as already-completed emits no second event, keeping the dead-man's-switch honest` |
| `duplicate_flagged` | `TELEMETRY-duplicate_flagged: builds a telemetry_events row…` | same pattern | `TELEMETRY-duplicate_flagged: the weekly scan emits one duplicate_flagged event per flagged pair, with its similarity score` | `TELEMETRY-duplicate_flagged (negative): a scan finding no near-duplicate pair emits no event` |
| `admin_manual_intervention` | `TELEMETRY-admin_manual_intervention: builds a telemetry_events row…` | same pattern | `TELEMETRY-admin_manual_intervention: an applied override emits one event carrying Lio's duration estimate verbatim` | `TELEMETRY-admin_manual_intervention (negative): a no-op override emits no event, so a retried no-op cannot inflate weekly admin time` |

Shape tests are in `tests/telemetry/eventShape.test.ts`; emission tests in
`tests/telemetry/emission.test.ts`; storage-level acceptance in
`tests/db/schema.test.ts`. Two registry guards also exist:
`TELEMETRY-REGISTRY: the shipped registry lists exactly the 8 required event
types and no others`, and `TELEMETRY-REGISTRY: an event type outside the
agreed 8 is rejected rather than silently stored` (both in code and in the
`telemetry_events` check constraint).

The end-to-end honesty of the `prediction_submitted` / `prediction_rejected_late`
pair is additionally proven against the real API and real Postgres by
`E2E-02`.

## 5. Deliberately not covered, and why

| Not covered | Reason |
|---|---|
| The 3 live fixture/results scraping adapters against their real sources | `02-architecture.v1.md` §1 states this is untestable in CI **by construction** and is covered by a production health-check alert instead. Adapters against *recorded fixtures* belong to the `fixture-ingestion` slice's own red gate, not this one; no adapter seam is asserted here beyond the normalized shape the domain consumes. |
| Player pseudo **spoofing** (submitting as someone else's exact pseudo) | An explicitly **accepted risk** — §7 Spoofing and ADR-0002. The system cannot distinguish the two, so there is no behaviour to assert. `NFR-DISCLOSE-01` therefore proves the reachable property (a request identifying as B never carries A's pick), not an unreachable one. |
| Rollback timing ("time to roll back an Edge Function deploy") | §6 says this is to be **measured at the pipeline gate**, not estimated — it is not a test. |
| Cost/free-tier limits (§4) | Not behaviour; nothing to assert in a test. |
| pg_cron scheduling itself | The tick functions take an injected `now` precisely so the *logic* is testable without the scheduler. That the cron job is actually registered is a deploy/pipeline concern; the dead-man's-switch in §6 is the production detection mechanism. |
| `duplicate_flags` review-status transitions beyond the contract shape | `updateDuplicateFlagStatus` is covered on both contract sides; its "never touches players or predictions" guarantee is covered by the AC-09 DB test asserting both players' rows survive. |
| Frontend rendering | Out of scope for this gate: AC-02's grey-out is asserted at the `buildFormRows` seam, which is the shared authority the UI must render; the DOM is not under test. |

## 6. Flags for the product owner

1. **RESOLVED.** NFR-RATE-01's threshold was an assumption, not an agreed
   number — `02-architecture.v1.md` §7 left it as "e.g. N/minute/IP". This
   suite assumed **10 requests per minute per IP** as a clearly-labelled
   placeholder (`ASSUMED_LIMIT` in `tests/unit/submitPrediction.test.ts`, and
   `SUBMIT_RATE_LIMIT_PER_MINUTE` in the expected `src/api/rateLimit.ts`).
   **Confirmed by Lio on 2026-08-03: 10 requests/minute/IP stands as the
   agreed value**, despite the noted household/office shared-IP tradeoff.
   No test changes needed — the tests were already written against the
   constant.

2. **RESOLVED.** `contracts/openapi.yaml` declares 8 operations;
   `02-architecture.v1.md` §5 said "9 operations". Schemathesis independently
   reported "Selected: 1/8"; §5's own prose enumerated the same 8 endpoints, so
   it was a miscount in the architecture doc's prose, not a missing endpoint.
   Corrected to "8" after this run, then the suite was re-run and produced the
   identical 118/117/1 result — this was documentation only.

3. **RESOLVED.** `contracts/db-schema.sql` contained no RLS statements,
   although §7 relies on "RLS blocks public INSERT/UPDATE on
   `predictions`/`games`/etc. entirely, so there's no PostgREST bypass".
   `NFR-RLS-01` and `NFR-RLS-02` are written against that mitigation. Added
   `enable row level security` on every table (no `anon`/`authenticated`
   policies granted, so those roles get no access at all — only
   `service_role`, used exclusively by Edge Functions, bypasses RLS). This is
   schema/DDL matching an already-frozen threat-model decision, not production
   business logic, so it was fixed directly rather than left for green. The
   suite was re-run after the change and produced the identical 118/117/1
   result: `tests/db/schema.test.ts` reads from `db/migrations/` (still
   absent, correctly — that's green-gate work), not from `contracts/db-schema.sql`
   directly, so this change could not and did not turn anything green
   prematurely. See `03-red-evidence.v1.md` §7.

4. **AC-08's "final scores are fetched"** is split across slices: this suite
   asserts the scoring/classement half (`runScoring`) and the exactly-once
   half. The *fetching* half belongs to `fixture-ingestion` and is covered
   there against recorded fixtures.
